# 구현 계획 (2단계) + 테스트 먼저 (3단계)

인자: 기능 이름 또는 `docs/specs/` 파일.

## 0. 크기 확인

- 크기가 정해지지 않았으면 `docs/workflow.md`의 기준으로 S/M/L을 제안하고 확정받는다.
- **S면 이 스킬을 쓰지 않는다.** 채팅으로 고칠 파일, 바꿀 내용, 추가할 테스트를 3~5줄로 말하고 "진행할까요?"로 승인받은 뒤 테스트 → 구현으로 간다.
- **L이면** 먼저 계획을 M 크기 여러 개로 나누는 안(001, 002, ...)을 채팅으로 제시하고 확정받는다. 이후 계획 하나씩 아래 절차를 반복한다.

## 2단계: 계획 (계획 모드)

1. `docs/specs/<기능>.md`를 읽는다. 없으면 `/spec`부터 하자고 말하고 멈춘다.
2. **`EnterPlanMode`로 계획 모드에 들어간다** (이미 계획 모드면 그대로). 계획 모드에서는 계획 파일 외에 파일을 수정할 수 없다.
3. 관련 코드, `docs/architecture.md`, `docs/decisions/`를 읽고 기존 구조를 파악한다.
4. 아래 양식대로 계획을 쓴다. **핵심 코드 스케치**는 판단이 들어가는 부분만 넣는다:
   - 핵심 메서드 시그니처와 분기 (정상·예외·경계)
   - 동시성·멱등성 처리 코드 (락, 원자 연산, upsert)
   - 유니크 제약·인덱스 DDL, 복잡한 쿼리
   - 컨트롤러·DTO처럼 정해진 구조대로 만드는 코드는 넣지 않는다.
5. **`ExitPlanMode`로 승인을 요청한다.** 계획 패널에 계획이 뜨고, 사용자가 승인해야 다음으로 넘어간다.
   승인 요청 전에 채팅으로 핵심 결정 2~3개와 "특히 테스트 목록을 봐 달라"는 말을 덧붙인다.
6. 거절·수정 요청이 오면 계획을 고쳐 다시 `ExitPlanMode`로 요청한다.

## 승인 직후: 계획 파일 저장

1. `ls docs/plans`로 마지막 번호를 확인하고 다음 번호(001부터)로 `docs/plans/<NNN>-<기능-kebab-case>.md`를 만든다.
2. 승인된 계획을 **그대로** 옮기고, 상태를 `승인됨 (YYYY-MM-DD)`로 적는다. 승인 과정에서 바뀐 점은 "변경 이력"에 적는다.

## 3단계: 테스트 먼저

1. 계획의 "테스트 목록"을 그대로 테스트 코드로 옮긴다. CLAUDE.md의 테스트 규칙(Given-When-Then, 백틱 한글 이름, Mockk)을 지킨다.
2. 단위 테스트는 Mockk, API는 `@SpringBootTest` + `MockMvc` 통합 테스트.
3. 테스트를 돌려 **구현이 없어서 실패하는 것**을 확인한다 (컴파일 실패는 시그니처만 만들어 해결).
4. 사용자에게 테스트 목록과 실패 상태를 보고하고, 구현은 `/new-api`로 이어간다.
