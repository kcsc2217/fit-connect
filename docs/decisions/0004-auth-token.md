# 0004 access는 JWT(HS256, 30분), refresh는 Redis에 둔 불투명 값으로 교체

- 상태: 채택
- 날짜: 2026-11-05
- 관련: docs/specs/auth-jwt.md, docs/plans/006-auth-jwt.md

## 배경
모든 API가 요청한 사용자를 알아야 한다. 서버를 여러 대로 늘려도 동작해야 하므로 서버 메모리에 로그인 상태를 둘 수 없다 (CLAUDE.md 아키텍처 원칙).
모바일 앱이라 쿠키 세션보다 헤더 토큰이 자연스럽고, 앱은 오래 로그인된 상태를 유지해야 한다.

## 선택지
### A. 서버 세션 (Spring Session + Redis)
- 장점: 로그아웃 즉시 무효화가 쉽다.
- 단점: 모든 요청이 Redis를 조회한다. 모바일 앱에서 쿠키·CSRF를 다뤄야 한다.

### B. access JWT만 (긴 수명)
- 장점: 저장소가 전혀 필요 없다.
- 단점: 탈취되면 만료까지 막을 방법이 없다. 로그아웃이 의미가 없다.

### C. 짧은 access JWT + Redis에 둔 refresh (갱신마다 교체)
- 장점: 요청마다 저장소를 조회하지 않는다 (서명·만료만 확인). refresh는 서버가 폐기할 수 있어 로그아웃·탈퇴가 동작한다. 교체로 탈취된 refresh의 재사용 창을 줄인다.
- 단점: 로그아웃 후에도 access는 만료(30분)까지 유효하다. 토큰 두 종류를 다뤄야 한다.

## 결정
C.
- access: JWT, HS256(서버 한 곳에서만 발급·검증하므로 대칭키), 30분, claim은 `sub`·`iat`·`exp`만. 검증 알고리즘은 서버가 고정한다.
- refresh: JWT가 아닌 랜덤 값 `"{userId}.{tokenId}"`(tokenId 256비트). Redis 키 `refresh:{userId}:{tokenId}`, TTL 14일. 기기마다 따로 둔다.
- 갱신은 Redis `DEL`의 반환값으로 "한 번만 쓰기"를 판정하고 새 refresh를 발급한다.
- 이미 쓰인 refresh가 다시 오면 그 요청만 401로 끝낸다. 사용자의 다른 refresh는 폐기하지 않는다.
- 만료(`TOKEN_EXPIRED`)와 그 밖의 무효(`UNAUTHORIZED`)를 다른 에러 코드로 준다. 앱은 만료일 때만 갱신한다.

## 이유
- 대부분의 요청이 저장소 조회 없이 끝나 지연과 Redis 부하가 작다.
- refresh를 JWT로 만들면 서버가 어차피 Redis를 봐야 폐기를 알 수 있어 서명의 이점이 없다. 불투명 값이 단순하다.
- 재사용 감지 시 전체 폐기(토큰 패밀리 무효화)는 네트워크 재시도만으로도 모든 기기를 로그아웃시킬 수 있다. 피해 범위가 access 수명 30분으로 제한되므로 그 요청만 거절한다.

## 결과
- 로그아웃은 refresh만 폐기한다. 즉시 차단이 필요해지면(관리자 정지 등) access 차단 목록을 그때 추가한다.
- 탈퇴는 `refresh:{userId}:*`를 모두 지워야 한다 (탈퇴 작업에서).
- 서명 키는 환경변수 `JWT_SECRET`으로만 받는다. 키를 바꾸면 모든 access가 무효가 된다 (refresh로 다시 받으면 된다).
- 소셜 로그인(카카오·구글 OIDC)은 `SocialTokenVerifier` 구현으로 붙이고, 토큰 발급 흐름은 이 결정을 그대로 쓴다.
