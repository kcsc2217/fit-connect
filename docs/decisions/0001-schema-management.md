# 0001 스키마 관리: 로컬 ddl-auto, 운영 Flyway, 테스트에서 validate

- 상태: 채택
- 날짜: 2026-11-01
- 관련: docs/db-schema.md, docs/plans/001-entity-rebuild-user.md

## 배경
1차 오픈 스키마(테이블 23개)를 엔티티로 옮기면서 테이블 생성·변경 방식을 정해야 했다.
운영에서는 테이블이 실수로 지워지거나 엔티티와 어긋난 채 배포되면 안 된다. 반면 개발 초기라 엔티티가 자주 바뀌어서, 로컬에서 바꿀 때마다 마이그레이션을 쓰는 건 부담이 크다. 개발자는 1명이고 Docker는 쓰지 않는다.

## 선택지
### A. 모든 환경에서 Flyway
- 장점: 로컬과 운영의 스키마가 항상 같다. 마이그레이션이 매일 실행돼서 오류가 일찍 드러난다.
- 단점: 엔티티를 바꿀 때마다 마이그레이션 파일을 같이 써야 해서 초기 개발이 느리다.

### B. 모든 환경에서 ddl-auto
- 장점: 가장 빠르다.
- 단점: 운영에서 쓸 수 없다 (`create`는 데이터를 지우고, `update`는 컬럼 삭제·이름 변경을 못 하고 이력이 남지 않는다).

### C. 로컬 ddl-auto=create, 운영 Flyway + validate, 테스트에서 둘을 비교
- 장점: 로컬 개발이 빠르고, 운영은 이력이 남는 마이그레이션으로 관리된다.
- 단점: 로컬에서는 마이그레이션이 돌지 않아 엔티티와 어긋나도 모른다.

## 결정
C. 단점을 막기 위해 테스트 프로파일에서 `fitness_test` DB에 Flyway 마이그레이션을 적용하고 `ddl-auto=validate`로 컨텍스트를 띄운다(`SchemaValidationTest`). 기본 설정(`application.yml`)은 운영 기준(Flyway + validate)으로 두고, 로컬 설정에서만 `create`로 덮어쓴다.

## 이유
- 초기 개발 속도와 운영 안전성을 둘 다 얻는다.
- 마이그레이션과 엔티티의 어긋남은 테스트(종료 시 테스트 훅, 이후 CI)에서 운영 배포 전에 잡힌다. 마이그레이션에서 컬럼 하나를 빼면 `missing column [withdrawn_at] in table [users]`로 실패하는 것을 확인했다.
- 기본값이 운영 기준이라, 프로파일을 빠뜨려도 테이블이 지워지지 않는다. 이를 위해 `application-local.yml`은 jar에서 뺀다(`build.gradle.kts`). jar에 들어가면 프로파일 없이 실행했을 때 기본 프로파일 local이 켜져 `create`가 적용된다(리뷰에서 발견).

## 결과
- **로컬(`create`)에서는 FK가 만들어지지 않는다.** 엔티티가 연관관계 없이 ID로만 참조하기 때문이다. 존재하지 않는 user_id로 저장해도 로컬에서는 성공하고, 테스트·운영(Flyway)에서만 실패한다. FK 위반 경로는 저장소 테스트로 확인한다.
- 테스트는 시작할 때마다 `clean`으로 테이블을 지운다. 환경변수가 테스트 DB 주소를 덮어써 다른 DB를 지우지 않도록, DB 이름이 `_test`로 끝날 때만 진행한다(`TestFlywayConfig`).
- 테이블을 바꿀 때는 마이그레이션과 엔티티를 함께 고쳐야 한다 (CLAUDE.md 규칙).
- 테스트는 로컬 MySQL이 켜져 있어야 돈다. Docker를 쓰게 되면 Testcontainers로 바꿔 CI에서도 같은 검증을 한다.
- validate는 컬럼 존재·타입만 본다. 인덱스·유니크·FK는 저장소 제약 테스트(`UserRepositoryConstraintTest` 등)로 따로 확인한다.
- 운영 첫 배포 이후에는 적용된 마이그레이션 파일을 고치지 않고 새 버전을 추가한다.
