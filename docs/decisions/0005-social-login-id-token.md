# 0005 소셜 로그인은 앱이 받은 id_token을 서버가 공개키로 검증한다

- 상태: 채택
- 날짜: 2026-11-09
- 관련: docs/specs/auth-social-oidc.md, docs/plans/007-auth-social-oidc.md, docs/decisions/0004-auth-token.md

## 배경
앱은 카카오·구글 SDK로 로그인한 뒤 서버에 "이 사람이 누구인지"를 증명해야 한다. 서버는 앱이 보낸 값을 그대로 믿을 수 없다 (누구나 로그인 API를 흉내 낼 수 있다). 1-A의 토큰 체계(ADR 0004)는 그대로 두고, 소셜 신원 확인 방식만 정한다.

## 선택지
### A. 소셜 access_token을 받아 서버가 사용자 정보 API를 호출
- 장점: 카카오·구글이 직접 확인해 준다. 구현이 단순하다.
- 단점: 로그인마다 외부 API를 호출한다 (지연, 회사 쪽 장애가 그대로 로그인 장애). 토큰이 우리 앱에 발급된 것인지(aud) 확인하려면 별도 API를 더 불러야 한다.

### B. OIDC id_token을 받아 서버가 공개키(JWKS)로 서명 검증
- 장점: 공개키를 캐시하면 로그인마다 외부를 부르지 않는다. 표준(OIDC)이라 카카오·구글을 같은 코드로 검증한다. `aud`로 우리 앱에 발급된 토큰인지 바로 안다.
- 단점: 공개키 캐시·키 교체·검증 규칙(iss, aud, exp, alg)을 직접 맞춰야 한다. id_token은 수명 동안 재사용될 수 있다.

## 결정
B. 카카오·구글 모두 OIDC id_token을 받는다.
- 검증: RS256 서명(공개키는 `kid`로 선택), `iss`(카카오 `https://kauth.kakao.com`, 구글 `https://accounts.google.com`·`accounts.google.com`), `aud`(설정한 앱 키·클라이언트 ID 중 하나), `exp`(필수, 30초 오차 허용), `sub`(1~100자). 사용자 식별자는 `sub`만 쓴다.
- 라이브러리: Spring Security의 `NimbusJwtDecoder`. 공개키 소스는 Nimbus `JWKSourceBuilder`로 직접 조립한다: 캐시 1시간, 모르는 `kid`일 때 다시 받기는 30초에 한 번, 1회 재시도, 장애 시 받아 둔 키를 12시간 사용, 연결·읽기 타임아웃 1초.
- 오류: 토큰 문제는 401 `INVALID_SOCIAL_TOKEN`, 공개키를 받지 못하면 503 `SOCIAL_LOGIN_UNAVAILABLE`.
- 재사용(replay) 방지는 하지 않는다 (nonce, 한 번만 사용 검사 없음).
- 소셜 이메일은 저장하지 않는다.

## 이유
- 대부분의 로그인이 외부 호출 없이 끝나 지연이 작고, 카카오·구글 장애가 받아 둔 키의 유효 기간(12시간) 동안은 로그인 장애로 번지지 않는다.
- Spring 기본 빌더가 쓰는 Nimbus `RemoteJWKSet`은 모르는 `kid`마다 공개키를 다시 받는다. 아무 `kid`나 넣은 토큰으로 카카오를 반복 호출하게 만들 수 있고, 카카오는 지나치게 잦은 요청을 차단할 수 있다고 안내한다. 그래서 다시 받기 횟수를 제한한다.
- Spring의 `JwtTimestampValidator`는 `exp`가 없는 토큰을 통과시킨다. 외부 토큰은 `exp`를 따로 필수로 검사한다.
- 재사용 방지를 하지 않는 이유: id_token은 앱↔카카오·구글↔우리 서버 사이 HTTPS로만 오가고, 탈취돼도 수명(구글 약 1시간, 카카오 약 2시간) 안에서만 쓸 수 있다. 서버 발급 nonce는 API와 앱 작업이 늘고, "한 번만 사용"은 앱의 네트워크 재시도까지 거절한다.

## 결과
- 받아들인 위험: 탈취된 id_token은 수명 안에서 로그인에 쓰일 수 있다. 위험이 커지면(웹 로그인 추가 등) 서버 발급 nonce를 도입한다.
- 허용 `aud`가 설정되지 않은 provider는 확인기를 만들지 않아 400 `UNSUPPORTED_PROVIDER`가 된다. 운영 배포 시 `KAKAO_APP_KEYS`, `GOOGLE_CLIENT_IDS`를 설정해야 한다.
- 키 교체 직후 30초 안에 또 새 `kid`가 오면 그 사이 401이 날 수 있다 (드묾).
- 공개키 캐시는 서버마다 메모리에 둔다. 로그인 상태가 아니라 공개된 키의 사본이라 서버 간 공유가 필요 없다.
- 애플 로그인도 OIDC라 같은 확인기에 설정만 추가하면 된다.
