# 온보딩: 내 몸·목표·장비·운동 일정 입력

- 요구사항: FR-03 (P0), US-02. FR-10(시작 강도)·FR-13(알림 시각)·FR-27(장비 기반 후보)의 입력값
- 상태: 확정 (2026-11-15)
- 작업 단위: 서버 009(M) → 앱 010(M)

## 목적
처음 가입한 사용자가 내 몸, 목표, 장비, 운동 요일, 알림 시각을 한 번만 입력하면, 이후 오늘의 운동이 이 정보로 만들어진다. 매번 다시 설명하지 않아도 된다.

## 범위
- 포함:
  - 서버: 온보딩 제출 API(프로필 + 장비 저장, 회원 상태 ONBOARDING → ACTIVE 전환), 내 프로필 조회 API, 입력 검증
  - 앱: "온보딩 준비 중" 자리 화면을 3단계 입력 화면(프로토타입 흐름)으로 교체, 제출 후 오늘 탭으로 이동, 건너뛰기 제거
- 제외 (다른 단계·기능):
  - 설정에서 온보딩 항목 수정 화면, 회원 탈퇴 → FR-04. 단 저장 API는 덮어쓰기라 수정 화면이 그대로 쓸 수 있게 만든다
  - 알림 예약·FCM 기기 토큰 등록 → 알림 기능 (FR-13). 온보딩은 알림 시각만 저장한다
  - 알림 시각·분할·장비 변경 시 재예약·재생성 → FR-15 (알림·오늘의 운동 기능)
  - 시작 강도 계산 → FR-10 (오늘의 운동). 온보딩은 경력·목표만 저장한다
  - 목표 칼로리 계산 → FR-30 (2차)
  - 체중 추이 기록 → 2차 (`user_profile.weight_kg`는 최신 값만)
  - 애플 로그인 회원 → FR-01 iOS 출시 시 (온보딩 흐름은 같음)

## 동작

### 앱 입력 흐름 (프로토타입 `onboard()` 3단계)
1. 로그인 결과 회원 상태가 ONBOARDING이면 온보딩 1단계로 간다 (지금의 자리 화면 위치).
2. **1단계 "몸 정보를 알려주세요"**: 키(cm), 몸무게(kg), 나이(세), 성별(남·여). 성별은 프로토타입에 없어 추가한다
3. **2단계 "어떤 몸을 만들고 싶나요?"**: 목표(감량·근비대·유지), 운동 경력(1년 미만·1~3년·3년 이상), 쓸 수 있는 장비(프리셋 헬스장 전체·덤벨만·맨몸 + "직접 고르기"로 10종 다중 선택)
4. **3단계 "언제 운동하나요?"**: 운동 요일(월~일 다중 선택), 분할 방식(전신·2분할·3분할), 알림 받을 시각(5분 단위), 운동 시간(30·45·60·90분). 운동 시간은 프로토타입에 없어 추가한다
5. 각 단계의 "다음"은 그 단계 입력이 유효할 때만 누를 수 있다. 위쪽 "이전"으로 돌아가면 입력한 값이 남아 있다.
6. 3단계의 "오늘의 운동 받기"를 누르면 모든 값을 한 번에 서버로 보낸다. 시간대는 기기 시간대를 함께 보낸다.
7. 성공하면 회원 상태가 ACTIVE가 되고 오늘 탭으로 간다. 앱을 다시 켜도 온보딩이 다시 나오지 않는다.

### 서버 제출 처리
1. 앱이 `PUT /api/v1/users/me/profile`로 프로필 전체와 장비 목록을 보낸다.
2. 서버가 값을 검증한다 (아래 규칙). 실패하면 아무것도 저장하지 않는다.
3. 한 트랜잭션 안에서:
   - `user_profile`을 덮어쓴다 (없으면 만들고, 있으면 모든 필드를 바꾼다)
   - `user_equipment`를 보낸 목록으로 바꾼다 (빠진 장비는 지우고 새 장비는 추가)
   - 회원 상태가 ONBOARDING이면 ACTIVE로 바꾼다. 이미 ACTIVE면 그대로 둔다
4. 저장된 프로필을 응답한다.

### 내 프로필 조회
- `GET /api/v1/users/me/profile`: 저장된 프로필과 장비를 돌려준다. 아직 온보딩 전이면 404.
- 앱 010에서 당장 쓰는 곳은 없다 (설정 화면 FR-04, 나 탭 요약에서 쓸 예정). 서버 009에서 저장 결과 확인과 통합 테스트용으로 함께 만든다.

## 규칙과 제약

### 값과 저장 형식
| 입력 | 앱 표시 | 서버 저장 | 검증 |
| --- | --- | --- | --- |
| 키 | cm, 소수 첫째 자리까지 | `height_cm DECIMAL(5,1)` | 100.0 ~ 250.0 |
| 몸무게 | kg, 소수 첫째 자리까지 | `weight_kg DECIMAL(5,1)` | 30.0 ~ 300.0 |
| 나이 | 세 | `birth_year SMALLINT`. 앱이 (올해 − 나이)로 바꿔 보낸다 | 서버는 (올해 − 100) ~ (올해 − 14) 범위만 받는다. 올해는 서버 `Clock` + 요청의 시간대 기준 |
| 성별 | 남·여 | `sex` MALE, FEMALE | 필수 |
| 목표 | 감량·근비대·유지 | `goal` CUT, BULK, MAINTAIN | 필수 |
| 운동 경력 | 1년 미만·1~3년·3년 이상 | `experience` BEGINNER, INTERMEDIATE, ADVANCED | 필수 |
| 장비 | 프리셋 3개 + 직접 고르기(10종) | `user_equipment` 행들 (Equipment 10종) | 중복은 하나로. 비어도 됨(맨몸만) |
| 운동 요일 | 월~일 다중 선택 | `workout_days` 비트마스크 (월=1 … 일=64) | 1개 이상. 요일 수와 분할 방식의 조합은 막지 않는다 (루틴 생성이 분할 순서를 이어 간다) |
| 분할 방식 | 전신·2분할·3분할 | `split_type` FULL_BODY, TWO_SPLIT, THREE_SPLIT | 필수 |
| 알림 시각 | 시:분 | `alarm_time TIME` (사용자 시간대 기준) | 5분 단위 (분이 5의 배수, 초 0) |
| 운동 시간 | 30·45·60·90분 중 선택 | `session_minutes SMALLINT` | 30, 45, 60, 90 중 하나 |
| 시간대 | 표시 안 함 (기기 값) | `timezone VARCHAR(40)` | IANA 시간대 이름(`ZoneId`로 해석 가능). 기본 Asia/Seoul |

- API 값은 enum 이름(영문)으로 주고받는다. 한글 표시는 앱이 정한다 (서버 에러 코드처럼 문구가 아니라 값으로 분기).
- 요일은 API에서 비트마스크 숫자가 아니라 요일 이름 목록(`["MONDAY","WEDNESDAY","FRIDAY"]`, Java `DayOfWeek` 이름)으로 주고받는다. 비트마스크는 서버 저장 형식이라 앱이 몰라도 되게 한다.
- 나이·시각 계산의 "오늘"은 서버 `Clock` 빈과 사용자 시간대 기준이다 (ADR 0002).

### 정합성
- 프로필 저장, 장비 교체, 상태 전환은 한 트랜잭션이다. 일부만 저장된 회원(프로필은 있는데 ONBOARDING, 또는 ACTIVE인데 프로필 없음)이 생기면 안 된다.
- **멱등:** 같은 요청을 두 번 보내도 결과가 같다 (덮어쓰기라서). 앱이 응답을 못 받고 다시 보내도 문제없다. `client_id`는 쓰지 않는다 (사용자당 프로필이 하나라 PK가 곧 멱등 키).
- **동시 제출:** 같은 사용자의 제출이 동시에 두 번 오면 (버튼 연타, 재전송) 한쪽이 PK 충돌로 실패하지 않고 둘 다 성공해야 한다. 최종 값은 마지막에 끝난 요청 기준. 방법은 계획에서 정한다.
- 성공 응답의 상태는 ACTIVE다. 앱은 응답을 받은 뒤에만 오늘 탭으로 간다.

### 비기능
- 신체 정보는 본인만 조회·수정한다 (경로에 userId 없음, 토큰의 userId만 사용). 로그에 신체 값을 남기지 않는다.
- p95 300ms 이하 (일반 API).

## 예외 상황
| 상황 | 기대 동작 (응답 코드·에러 코드) |
| --- | --- |
| 필수 값 누락, 범위 밖, 모르는 enum 값, 잘못된 시간대 | 400 `INVALID_INPUT` (ADR 0003 형식, 어느 필드인지 `errors`에 담음 — 기존 검증 에러 형식을 따른다) |
| 운동 요일 0개, 알림 시각이 5분 단위가 아님, 운동 시간이 선택지 밖 | 400 `INVALID_INPUT` |
| 인증 없음·만료 | 401 `UNAUTHORIZED`·`TOKEN_EXPIRED` (기존 필터) |
| 토큰은 유효한데 회원이 없음 | 404 `NOT_FOUND` (앱은 fix/startup-missing-user와 같게 로그인 화면으로) |
| 탈퇴한 회원(WITHDRAWN) | 403 `FORBIDDEN`. 탈퇴 API가 아직 없어 지금은 생길 수 없고, 정확한 처리는 FR-04에서 다시 정한다 |
| 이미 ACTIVE인 회원이 다시 제출 | 200, 덮어쓰기 (FR-04 수정 화면이 같은 API 사용) |
| 온보딩 전 프로필 조회 | 404 `NOT_FOUND` |
| 앱: 제출 중 연결 끊김 | 입력값 유지, "연결을 확인해 주세요" + 다시 보내기. 상태는 그대로 ONBOARDING |
| 앱: 제출 중 서버 오류 | 입력값 유지, "문제가 생겼어요" + 다시 보내기 |
| 앱: 제출이 `INVALID_INPUT` | 입력값 유지, "입력한 정보를 다시 확인해 주세요". 앱 검증을 통과했어도 생길 수 있다 (아래 알려진 한계) |
| 앱: 온보딩 도중 앱 종료 | 입력값을 기기에 남기지 않는다. 다시 켜면 1단계부터 (3단계라 1분 이내) |

### 알려진 한계
- **출생 연도 경계:** 앱은 나이를 출생 연도로 바꿀 때 기기 시계·시간대로 "올해"를 정하고, 서버는 요청의 `timezone`과 서버 시계로 정한다. 연말·연초의 몇 초 사이, 기기 시계가 틀린 기기, 시간대 읽기에 실패해 `Asia/Seoul`로 대체된 해외 기기에서는 둘이 어긋나 나이 14세·100세가 400 `INVALID_INPUT`이 될 수 있다. 영향이 경계 나이와 짧은 시간에 한정돼 서버 API는 바꾸지 않고, 앱이 문구를 구분한다 (계획 010 리뷰 1). 나이를 서버가 받아 계산하는 방식은 FR-04 때 다시 검토한다.

## 데이터
- 테이블은 이미 있다 (V1, 계획 001). **스키마 변경 없음**이 목표.
  - `user_profile` (PK `user_id`, 위 컬럼들, 인덱스 `(alarm_time)`)
  - `user_equipment` (PK `(user_id, equipment)`)
  - `users.status` (ONBOARDING → ACTIVE)
- 엔티티 `UserProfile`, `UserEquipment`, `User`가 있다. `UserProfile.workoutDays`는 0~127 범위 검증이 이미 있다.
- 제품 지표용 `event_log`의 온보딩 완료 이벤트는 이번에 남기지 않는다. 제품 지표 기록을 시작하는 작업에서 한꺼번에 붙인다.

## API 초안
| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| PUT | /api/v1/users/me/profile | 온보딩 제출 = 프로필·장비 덮어쓰기 + ONBOARDING이면 ACTIVE. 200 + 저장된 프로필 |
| GET | /api/v1/users/me/profile | 내 프로필·장비 조회. 온보딩 전이면 404 |

요청 예시 (값 이름은 계획에서 확정):
```json
{
  "heightCm": 175.0,
  "weightKg": 72.5,
  "birthYear": 1997,
  "sex": "MALE",
  "goal": "BULK",
  "experience": "INTERMEDIATE",
  "equipment": ["BARBELL", "DUMBBELL", "BENCH", "RACK"],
  "workoutDays": ["MONDAY", "WEDNESDAY", "FRIDAY"],
  "splitType": "THREE_SPLIT",
  "alarmTime": "19:00",
  "timezone": "Asia/Seoul",
  "sessionMinutes": 60
}
```
- 응답은 요청과 같은 모양 + `status`(ACTIVE). 엔티티가 아니라 DTO로 반환한다.
- `GET /api/v1/users/me`의 `status`도 ACTIVE로 바뀌므로 앱 시작 판정은 지금 그대로 동작한다.

## 경계
- **user 모듈 안에서 끝난다.** 프로필·장비·회원 상태 모두 user 모듈 테이블이다.
- 이후 기능이 읽어 간다 (user 모듈 Service를 통해서만):
  - 오늘의 운동(routine): 경력·목표(시작 강도), 분할, 운동 요일, 세션 시간, 장비 → `ExerciseService.findCandidates(bodyParts, equipments)`의 장비 입력
  - 알림(notification): 알림 시각, 시간대, 운동 요일
- `common.type.Equipment`, `common.type.Experience`는 workout 모듈과 같이 쓰는 값이라 그대로 쓴다.

## 프리셋 장비 매핑 (앱)
| 프리셋 | 보내는 장비 |
| --- | --- |
| 헬스장 전체 | 10종 모두 |
| 덤벨만 | DUMBBELL, BENCH, BODYWEIGHT |
| 맨몸 | BODYWEIGHT, PULLUP_BAR |
| 직접 고르기 | 사용자가 고른 것 (0개도 가능 → 맨몸 종목만 후보) |

- 서버는 프리셋을 모른다. 항상 장비 목록만 받는다. 프리셋 이름은 앱 표시용이다.
