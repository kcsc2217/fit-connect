# 운동 기록: 세트 기록과 오프라인 동기화

- 요구사항: FR-20, FR-21, FR-22, FR-23, FR-28 (모두 P0), FR-25의 일부. US-05, US-06. 비기능 "정합성: 기록 중복·유실 0건"
- 상태: 확정 (2026-11-24)
- 작업 단위: L. 서버 011(동기화 API + 종목 조회, M) → 앱 012(기록 화면 + 기기 저장소 + 자동 전송, M)

## 목적
헬스장 지하처럼 연결이 끊긴 곳에서도 세트를 탭 한 번으로 기록하고, 연결되면 자동으로 서버에 올라가 유실·중복 없이 남는다. 이 기록이 이후 오늘의 운동(무게 계산, FR-10)의 입력이 된다.

## 범위
- 포함:
  - 서버: 세션·세트 묶음 동기화 API(최대 100건, `(user_id, client_id)` upsert, last-write-wins, tombstone), 종목 사전 조회 API(앱이 종목을 고르고 `exercise_id`를 쓰기 위해)
  - 앱: 운동 시작 → 종목 고르기 → 세트 기록(빠른 기록) → 휴식 타이머 → 운동 마치기, 기기에 먼저 저장, 연결되면 자동 전송, 전송 대기 표시
  - 운동 완료 화면: 세트 수·시간·볼륨 요약 (기기에서 계산)
- 제외 (다른 단계·기능):
  - 오늘의 루틴으로 운동 시작(처방된 무게·횟수를 기본값으로) → 오늘의 운동 기능 (FR-10~12). 이번에는 "자유 기록"으로 시작하고 `routine_id`를 비워 둔다
  - 세션 종료 이벤트로 개인 최고 기록·주간 볼륨 갱신(FR-24), 완료 화면의 PR 표시 → 운동 기록 바로 다음 M
  - 난이도 피드백(쉬웠어요·적당했어요·힘들었어요) → `daily_routine.feedback`에 저장되므로 오늘의 운동 기능 (FR-25 나머지)
  - 사용자 종목 추가 → FR-26 (2차)
  - 여러 기기 간 동기화·서버 기록 내려받기(재설치 복원) → 이번에는 올리기(push)만. 앱 저장소가 기준이다
  - 기록 화면(지난 운동 목록, 주간 볼륨 추이) → FR-70 (2차)

## 동작

### 앱: 운동 기록 (프로토타입 `session()`)
1. 오늘 탭에서 "운동 시작"을 누르면 세션을 만든다. 앱이 `client_id`(UUID)를 만들고 시작 시각과 함께 기기에 저장한다.
2. **자유 기록:** 종목 사전에서 직접 고른다 (이름 검색·부위 필터). 오늘의 운동 기능이 생기면 루틴에서 시작하는 경로를 더한다
3. 종목 화면: 종목 이름, 큰 무게 표시, 세트 줄들(번호·무게·횟수·완료 체크).
   - **빠른 기록 (FR-28):** 세트 줄의 기본값은 같은 세션의 앞 세트 값, 없으면 그 종목의 지난 기록 값, 그것도 없으면 빈 값. 다를 때만 고치고, 오른쪽 체크를 한 번 누르면 완료로 기록된다.
   - 완료하면 종목의 기본 휴식 시간(`exercise.default_rest_sec`)으로 휴식 타이머가 뜬다. 건너뛸 수 있다.
   - 세트 추가·삭제, 완료 취소가 된다. 삭제는 tombstone으로 남긴다.
4. 다음 종목으로 넘어가거나 종목을 더한다.
5. "운동 마치기"를 누르면 세션 종료 시각을 저장하고 완료 화면(세트 수, 운동 시간, 볼륨 = Σ 무게 × 횟수, 완료 세트만)을 보여 준다.
6. 모든 변경은 기기 저장소에 먼저 쓰고, 바뀐 항목은 "전송 대기"로 표시한다.

### 앱: 동기화 (FR-21)
1. 전송 대기 항목이 있고 연결돼 있으면, 최대 100건씩 묶어 서버로 보낸다. 세션은 그 세션의 세트보다 먼저(같은 묶음이면 앞에) 보낸다.
2. 서버가 항목별 결과를 돌려주면 성공한 항목만 "전송 완료"로 바꾼다. 실패한 항목은 이유에 따라 다시 보내거나(연결·서버 오류) 버린다(검증 실패: 앱은 로그만 남기고 기기 기록은 그대로 둔다).
3. 보내는 시점: 기록이 바뀐 직후(짧게 모아서), 앱이 앞으로 올 때, 연결이 돌아올 때. 실패하면 점점 간격을 늘려 다시 시도한다.
4. 화면에는 연결이 끊겼을 때 "기록은 휴대폰에 저장되고, 연결되면 자동으로 보내요. 지금 N개가 전송을 기다리고 있어요"를 보여 준다 (프로토타입 문구).

### 서버: 묶음 동기화 (FR-22, FR-23)
1. 앱이 `POST /api/v1/workouts/sync`로 세션·세트 변경을 최대 100건 보낸다.
2. 항목마다:
   - `(user_id, client_id)`로 기존 행을 찾는다. 없으면 만든다.
   - 있으면 `client_updated_at`을 비교한다. 요청 값이 더 새로우면 덮어쓰고, 같거나 오래됐으면 무시한다 (last-write-wins). 무시해도 성공으로 본다 (멱등).
   - 삭제는 `deleted = true`로 남긴다(tombstone). **삭제된 행은 되살리지 않는다:** 이미 삭제된 행에 온 수정은 시각과 관계없이 무시한다(`IGNORED`).
   - 세트는 세션을 `session_client_id`로 가리킨다. 서버가 같은 사용자의 세션 행을 찾아 `session_id`를 채운다.
3. 항목별 결과(성공·무시·실패와 이유)를 돌려준다. 한 항목의 실패가 다른 항목을 막지 않는다.
4. `server_received_at`에 서버 수신 시각을 남긴다 (기기 시계 어긋남 확인용).

### 서버: 종목 사전 조회
- `GET /api/v1/exercises`: 활성 종목 목록(id, code, 한글 이름, 부위, 부하 방식, 기본 휴식 시간). 앱이 기기에 저장해 두고 오프라인에서도 고를 수 있게 한다. 사용자 장비로 거르지 않는다 (기록은 장비와 관계없이 할 수 있어야 함).

## 규칙과 제약
- **멱등:** 같은 묶음을 여러 번 보내도, 응답을 못 받고 다시 보내도 행은 한 번만 생긴다 (`(user_id, client_id)` 유니크 + upsert). 동시에 같은 항목이 두 번 와도 중복 행이 생기면 안 된다 (방법은 계획에서 정함).
- **충돌:** 클라이언트 수정 시각 기준 last-write-wins. `client_updated_at`이 서버 수신 시각보다 5분 넘게 미래면 서버 수신 시각으로 낮춰 저장한다 (미래로 틀어진 기기 시계가 이후 모든 수정을 영원히 이기는 것 방지).
- **묶음 크기:** 한 요청 최대 100건(세션 + 세트). 넘으면 400.
- **소유권:** 다른 사용자의 세션을 가리키는 세트, 다른 사용자의 `client_id`는 그 사용자의 행으로 취급하지 않는다 (유니크 범위가 사용자 단위).
- **값 검증:** 무게 0~999.99kg(소수 둘째 자리), 반복 1~999, RPE 1.0~10.0(0.5 단위), 순서 0 이상, 존재하는 활성 종목, 시작 ≤ 종료.
- **삭제된 세션의 세트:** 삭제된 세션을 가리키는 세트도 저장한다(동기화는 막지 않음). 세트를 읽어 쓰는 쪽(오늘의 운동 무게 계산, FR-24 PR·주간 볼륨, 챌린지 인증)은 **삭제된 세트와 삭제된 세션에 속한 세트를 빼고** 읽는다 (011 리뷰 결정)
- **시각 범위:** `startedAt`·`endedAt`·`performedAt`은 2000-01-01 ~ 서버 시각+1일, `clientUpdatedAt`은 2000-01-01 이후만 받는다(미래 쪽은 서버 시각으로 낮춤). 범위 밖은 그 항목만 `INVALID_VALUE`
- **유실 0건:** 서버가 성공을 돌려준 항목만 앱이 전송 완료로 바꾼다. 앱을 끄거나 재시작해도 전송 대기 항목은 남는다.
- **성능:** 100건 묶음 처리 p95 300ms 이하를 목표로 하고, 묶음 저장 전후 처리량을 잰다 (PRD 기술 지표 "동기화").

## 예외 상황
| 상황 | 기대 동작 (응답 코드·에러 코드) |
| --- | --- |
| 묶음이 100건 초과, 빈 묶음, 형식 오류, 목록에 빈 원소(`null`), 한 묶음에 같은 clientId 두 번 | 400 `INVALID_INPUT` (묶음 전체 거절) |
| 같은 회원의 다른 동기화가 5초 넘게 진행 중 | 503 `SYNC_BUSY`, 앱은 잠시 뒤 다시 보냄 |
| 항목 하나의 값이 범위 밖·모르는 종목 | 그 항목만 실패(이유 코드), 나머지는 저장. 응답은 200 |
| 세트가 가리키는 세션이 서버에 없음 | 그 세트만 실패(`SESSION_NOT_FOUND`), 앱은 세션을 보낸 뒤 다시 보냄 |
| 이미 삭제된 행에 수정이 옴 | 무시(`IGNORED`), 성공으로 응답 (되살리지 않음) |
| 수정 시각이 서버 시각보다 5분 넘게 미래 | 저장은 하되 `client_updated_at`을 서버 수신 시각으로 낮춤 |
| 같은 항목을 다시 보냄 | 성공(무시됨), 행은 하나 |
| 오래된 수정이 늦게 도착 | 무시(새 값 유지), 성공으로 응답 |
| 인증 만료 | 401 `TOKEN_EXPIRED` → 앱 인터셉터가 갱신 후 다시 보냄 (기존) |
| 탈퇴 회원 | 403 `FORBIDDEN` (온보딩과 같게) |
| 앱: 연결 끊김 | 기록은 계속 기기에 저장, 전송 대기 수 표시, 연결되면 자동 전송 |
| 앱: 서버 오류(500) | 다시 시도 (간격을 늘려 가며) |

## 데이터
- 테이블은 이미 있다 (V2, 계획 002). **스키마 변경은 없거나 작게** 하는 것이 목표.
  - `workout_session`: `client_id`, `routine_id`(이번엔 null), `started_at`, `ended_at`, `condition_note`, `deleted`, `client_updated_at`, `server_received_at`. 유니크 `(user_id, client_id)`, 인덱스 `(user_id, started_at)`
  - `workout_set`: `client_id`, `session_id`(FK), `exercise_id`(FK), `exercise_order`, `set_order`, `weight_kg`, `reps`, `rpe`, `completed`, `deleted`, `performed_at`, `client_updated_at`. 유니크 `(user_id, client_id)`
  - `exercise`: 조회만
- 확인할 점 (계획에서): `workout_set`에 `server_received_at`이 없다(세션에만 있음). 세트의 `exercise_id`는 엔티티에서 바꿀 수 없게(`val`) 되어 있어, 종목을 바꾸려면 세트를 지우고 새로 만든다.
- 앱: 기기 저장소(로컬 DB)에 세션·세트·전송 상태·종목 사전을 둔다. 패키지는 계획에서 고른다.

## API 초안
| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | /api/v1/workouts/sync | 세션·세트 변경 묶음(최대 100건) upsert. 200 + 항목별 결과 |
| GET | /api/v1/exercises | 활성 종목 사전 |

요청 예시 (필드 이름은 계획에서 확정):
```json
{
  "sessions": [
    { "clientId": "8f1c…", "startedAt": "2026-11-24T10:00:00Z", "endedAt": null,
      "conditionNote": null, "deleted": false, "clientUpdatedAt": "2026-11-24T10:00:00Z" }
  ],
  "sets": [
    { "clientId": "a2b3…", "sessionClientId": "8f1c…", "exerciseId": 1, "exerciseOrder": 0, "setOrder": 0,
      "weightKg": 60.0, "reps": 8, "rpe": null, "completed": true, "deleted": false,
      "performedAt": "2026-11-24T10:05:00Z", "clientUpdatedAt": "2026-11-24T10:05:00Z" }
  ]
}
```
응답 예시:
```json
{ "results": [ { "clientId": "8f1c…", "type": "SESSION", "outcome": "APPLIED" },
               { "clientId": "a2b3…", "type": "SET", "outcome": "FAILED", "reason": "SESSION_NOT_FOUND" } ] }
```
- `outcome`: `APPLIED`(저장·갱신), `IGNORED`(더 새로운 값이 이미 있음), `FAILED`(+ `reason`)

## 경계
- **workout 모듈 안에서 끝난다** (세션·세트·종목 모두 workout 소유).
- user 모듈: 탈퇴 회원 확인이 필요하면 user 모듈 Service를 통해서만 (Repository 직접 주입 금지).
- 이후 기능이 읽어 간다 (삭제된 세트와 삭제된 세션의 세트는 빼고): 오늘의 운동(최근 2주 기록, 인덱스 `(user_id, exercise_id, performed_at)`), FR-24 집계(세션 종료 이벤트), 챌린지 자동 인증(FR-57).
- `routine_id`는 routine 모듈 ID지만 이번에는 쓰지 않는다.
