# 앱 뼈대: 로그인 → 내 정보 (Flutter, iOS 우선)

- 요구사항: FR-01·FR-02의 앱 쪽 (P0), 착수 계획 2단계 "뼈대 + CI"(서버 API 하나 ↔ Flutter 화면 연결), 원본 기능 명세 1차 3번 "Flutter 앱 뼈대: 로그인 화면, 탭 구조, API 연동"
- 비기능: 보안(비밀값은 코드 밖, 토큰은 기기 보안 저장소), PRD 리스크 "앱 개발에 시간 과다 소요 → 최소 화면"
- 상태: 확정 (2026-11-12)
- 선행: docs/specs/auth-jwt.md (1-A), docs/specs/auth-social-oidc.md (1-B), docs/decisions/0003·0004·0005

## 목적
사용자가 앱을 열어 카카오나 구글로 로그인하면, 다음부터는 다시 로그인하지 않고 바로 앱을 쓴다. 이번 작업은 이후 모든 화면이 올라갈 앱의 바탕(폴더 구조, 테마, 서버 호출, 인증 처리, CI)을 만드는 것이 핵심이다.

## 동작

### 앱 시작
1. 기기 보안 저장소에서 refresh 토큰을 읽는다.
2. 없으면 로그인 화면으로 간다.
3. 있으면 `GET /api/v1/users/me`를 호출해 본다 (access가 만료됐으면 아래 "자동 갱신"을 거친다).
   - 성공: 응답의 `status`로 화면을 정한다 (`ACTIVE` → 메인 탭, `ONBOARDING` → "온보딩 준비 중" 자리 화면. 자리 화면의 "건너뛰기"로 메인 탭에 갈 수 있다. 열린 질문 3).
   - 갱신까지 실패(`INVALID_REFRESH_TOKEN` 등 401): 저장된 토큰을 지우고 로그인 화면으로 간다.
   - 네트워크 실패: 토큰은 지우지 않고 "연결을 확인해 주세요"와 다시 시도 버튼을 보여준다.

### 로그인
1. 사용자가 "카카오로 시작하기" 또는 "Google로 시작하기"를 누른다.
2. 앱이 소셜 SDK로 로그인해 id_token을 받는다.
   - 카카오: 카카오 SDK. 시뮬레이터에는 카카오톡이 없으므로 카카오계정(웹) 로그인으로 진행된다. 콘솔에서 OpenID Connect가 켜져 있어야 id_token이 나온다.
   - 구글: Google Sign-In SDK. id_token의 `aud`가 서버 허용 클라이언트 ID 목록에 있어야 한다.
3. `POST /api/v1/auth/login {"provider": "KAKAO" | "GOOGLE", "token": "<id_token>"}`을 보낸다.
4. 응답의 access·refresh·각 만료 시각을 보안 저장소에 저장한다.
5. 응답의 `status`로 화면을 정한다 (앱 시작 3번과 같음).

### 자동 갱신
1. 인증이 필요한 요청이 401 `TOKEN_EXPIRED`를 받으면 `POST /api/v1/auth/refresh {"refreshToken": ...}`를 보낸다.
2. 성공하면 새 access·refresh를 저장하고 원래 요청을 한 번 다시 보낸다.
3. 실패(401 `INVALID_REFRESH_TOKEN`)하면 토큰을 지우고 로그인 화면으로 보낸다.
4. 401이어도 `code`가 `TOKEN_EXPIRED`가 아니면(`UNAUTHORIZED`) 갱신하지 않고 3번처럼 처리한다 (ADR 0004: 앱은 만료일 때만 갱신).

### 내 정보 ("나" 탭)
1. `GET /api/v1/users/me`로 닉네임, 상태, 가입일, 연결된 소셜 종류를 보여준다.
2. 로그아웃 버튼.

### 로그아웃
1. `POST /api/v1/auth/logout {"refreshToken": ...}`을 보낸다.
2. 응답과 관계없이(네트워크 실패 포함) 기기의 토큰을 지우고 로그인 화면으로 간다. 서버 쪽 refresh는 14일 뒤 자연히 만료된다.
3. 소셜 SDK의 로그인 상태도 끊는다 (다음 로그인 때 계정을 다시 고를 수 있게, 열린 질문 5).

## 규칙과 제약
- **갱신은 동시에 한 번만.** refresh는 한 번만 쓸 수 있다(ADR 0004). 여러 요청이 동시에 `TOKEN_EXPIRED`를 받아도 갱신 요청은 하나만 보내고, 나머지는 그 결과를 기다렸다가 새 access로 다시 보낸다. 두 번 보내면 두 번째가 `INVALID_REFRESH_TOKEN`이 되어 멀쩡한 사용자가 로그아웃된다.
- 재요청은 한 번만 한다 (갱신 후에도 401이면 로그인 화면으로).
- 토큰은 iOS Keychain(보안 저장소)에만 둔다. 일반 저장소(SharedPreferences 등)와 로그에 남기지 않는다. id_token도 로그에 남기지 않는다.
- 서버 주소, 카카오 네이티브 앱 키, 구글 클라이언트 ID는 코드에 넣지 않는다. 빌드할 때 넘기는 값(커밋하지 않는 로컬 파일)으로 받는다. 서버 쪽 허용 `aud` 설정과 짝이 맞아야 한다.
  - 카카오 네이티브 앱 키와 구글 클라이언트 ID는 앱에 포함되어 배포되므로 엄밀한 비밀값은 아니다. 다만 환경마다 다르고 저장소에 둘 이유가 없어 같은 방식으로 다룬다.
- 에러 분기는 문구(`detail`)가 아니라 `code`로 한다 (ADR 0003).
- 개발용 로그인(`provider: DEV`)은 개발 빌드에서만 버튼이 보인다. 서버도 로컬·테스트 설정에서만 받는다(1-A). 키 없이 화면·토큰 흐름을 확인하는 용도다 (열린 질문 2).
- 앱 상태 관리는 Riverpod, HTTP는 Dio (원본 기능 명세 기술 스택).
- 최소 화면 원칙: 이번에 만드는 화면은 로그인, 메인 탭 틀, 내 정보, 자리 화면뿐이다.
- 테스트: 위젯 테스트로 화면 분기를, 단위 테스트로 토큰 갱신 규칙을 검증한다. 소셜 SDK와 서버는 가짜로 바꿔 끼운다. CI는 `flutter analyze` + `flutter test`.

## 예외 상황
| 상황 | 기대 동작 |
| --- | --- |
| 사용자가 소셜 로그인 창을 닫음 | 로그인 화면에 그대로 남음. 에러 표시 없음 |
| 소셜 SDK 오류 (설정 누락, id_token 없음 등) | "로그인하지 못했어요. 다시 시도해 주세요" |
| 401 `INVALID_SOCIAL_TOKEN` | 위와 같은 안내 (소셜 로그인을 다시 시도하게 함) |
| 503 `SOCIAL_LOGIN_UNAVAILABLE` | "잠시 후 다시 시도해 주세요". 소셜 로그인을 다시 시키지 않음 (1-B) |
| 400 `UNSUPPORTED_PROVIDER` | "지금은 이 방법으로 로그인할 수 없어요" (서버에 aud 설정이 없을 때) |
| 서버 연결 실패·타임아웃 | "연결을 확인해 주세요" + 다시 시도. 저장된 토큰은 지우지 않음 |
| 401 `TOKEN_EXPIRED` | 자동 갱신 후 원래 요청 재시도 (사용자에게 보이지 않음) |
| 갱신 실패 401 `INVALID_REFRESH_TOKEN`, 401 `UNAUTHORIZED` | 토큰 삭제, 로그인 화면 |
| 동시에 여러 요청이 `TOKEN_EXPIRED` | 갱신 요청 1번, 나머지는 새 access로 재시도 |
| 로그아웃 요청 실패 | 기기 토큰은 지우고 로그인 화면으로 이동 |
| 예상하지 못한 응답 (500 `INTERNAL_ERROR`, 형식이 다른 응답) | "문제가 생겼어요. 잠시 후 다시 시도해 주세요" |

## API 초안 (앱이 호출하는 서버 API, 모두 기존)
| 메서드 | 경로 | 앱에서 쓰는 곳 |
| --- | --- | --- |
| POST | /api/v1/auth/login | 로그인 버튼 |

## 경계
- 서버 `user` 모듈: API 계약은 auth-jwt.md, auth-social-oidc.md를 그대로 따른다. 이번 작업에서 서버 코드는 바꾸지 않는다.
- 서버 설정: 로컬 서버의 `KAKAO_APP_KEYS`, `GOOGLE_CLIENT_IDS`에 앱이 쓰는 카카오 앱 키·구글 iOS 클라이언트 ID가 들어 있어야 실제 소셜 로그인이 된다. 개발용 로그인은 `fitness.auth.dev-login.enabled=true`(로컬)일 때만 된다.
- 시뮬레이터 → 로컬 서버: iOS 시뮬레이터는 `localhost`로 Mac의 서버(8080)에 바로 붙는다. 로컬은 http라 iOS의 http 차단(ATS)을 로컬 주소에 한해 푼다 (`NSAllowsLocalNetworking`). 출시 빌드에도 들어가지만 출시 빌드는 https 서버를 쓰므로 효과가 없다 (계획 008).
- 온보딩 작업: `status = ONBOARDING`일 때 갈 화면 자리를 이번에 만들고, 온보딩 작업이 내용을 채운다.
- CI: 앱 작업(Flutter)은 `app/`이 바뀔 때만 돈다. 서버 작업(Gradle `test`)은 `main` 보호 규칙의 필수 체크라 경로와 관계없이 항상 돈다 (계획 008).
- 카카오·구글 개발자 콘솔 등록(번들 ID, URL 스킴, OpenID Connect 켜기)은 사용자가 한다. 실제 소셜 로그인 확인 전까지만 있으면 된다.
