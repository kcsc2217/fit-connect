# 트래픽 설계 (초안)

- 상태: 초안 (가정 수치는 실사용자 검증 후 조정)
- 기준: `docs/prd.md` 5장(기술 지표)·9장(비기능 요구사항), `docs/architecture.md`, `docs/db-schema.md`
- 관련: `docs/workflow.md` 6단계(성능 확인), `docs/templates/load-test.md`

이 문서는 "사용자가 늘면 어디가 먼저 버티지 못하는가"를 미리 정하고, 각 지점의 설계와 부하 테스트 기준을 한곳에 모은다. 기능별 계획(`docs/plans/`)을 쓸 때 해당 API의 목표 수치는 여기서 가져온다.

## 1. 전제

- 실사용자는 지인 규모로 시작한다 (PRD 비목표: 대규모 사용자 확보). 그래서 트래픽 성과는 **가정 → 설계 → 부하 테스트로 재현 → 측정**으로 만든다.
- 운영 서버에서는 부하 테스트를 하지 않는다. 운영과 같은 사양의 스테이징에서 한다 (7장).
- 기술 선택은 측정으로 필요가 확인될 때만 늘린다 (카프카, 읽기 복제본, 샤딩 등).

## 2. 가정 수치

설계 목표 규모는 **가입자 10만 명**이다. 한계를 찾는 스트레스 테스트는 그 5배(50만 명)로 한다.

| 항목 | 가정 | 근거 |
| --- | --- | --- |
| 가입자 | 100,000 | 설계 목표 (스트레스: 500,000) |
| 오늘이 운동일인 비율 | 43% (주 3회 ÷ 7) | 페르소나: 주 3회 |
| 가장 많이 몰리는 알림 시각의 비중 | 30% (예: 19:00) | 퇴근 후 운동 페르소나. 실데이터로 교체 |
| 알림 열람률 | 50% | PRD 제품 지표 목표 |
| 연 사람 중 첫 10초 안에 여는 비율 | 40% | 가정. 푸시 직후 열람 분포를 실측해 교체 |
| 앱을 한 번 열 때 나가는 요청 수 | 3 | 내 정보, 오늘의 운동, 이벤트 기록 (토큰 갱신은 가끔) |
| 루틴 완료율 | 60% | PRD 제품 지표 목표 |
| 세션당 세트 수 | 25 | 종목 5~6개 × 4~5세트 |

> 숫자는 모두 가정이다. 실사용자 2주 검증(PRD 6장) 뒤 알림 시각 분포와 열람 분포부터 실측값으로 바꾼다.

## 3. 어디가 몰리나

| 순위 | 지점 | 성격 | 병목 |
| --- | --- | --- | --- |
| 1 | 알림 시각: 루틴 생성 → 푸시 → 푸시 직후 조회 | 시각에 묶인 급증 (쓰기 배치 + 외부 API + 읽기 급증) | LLM 호출 한도, FCM 발송 처리량, 캐시 미스 시 DB |
| 2 | 운동 기록 쓰기와 오프라인 동기화 | 초당 요청은 적고 **데이터가 빨리 쌓임** | 테이블 크기, 인덱스, 멱등 upsert 비용 |
| 3 | 챌린지 선착순 신청 | 오픈 순간 급증, 정합성 | 같은 행·키에 몰리는 경합 |

챌린지는 동시성 기법 비교 실험으로 두고, 운영 트래픽 설계의 중심은 1·2번이다. 이 앱만의 문제이고, 사용자 수에 비례해 커지며, 핵심 루프(오늘의 루틴 → 기록 → 다음 루틴)에 붙어 있기 때문이다.

### 3.1 알림 시각 계산 (설계 목표 10만 명)

| 단계 | 계산 | 결과 |
| --- | --- | --- |
| 19:00 알림 대상 | 100,000 × 0.43 × 0.30 | 약 **13,000명** |
| 생성 기간 (알림 30분 전부터) | 13,000 ÷ 1,800초 | 평균 **약 7건/초** (약 430 RPM) |
| LLM 동시 호출 수 | 7건/초 × 응답 8초(가정) | 약 **60개** 동시 |
| 푸시 발송 | 13,000건을 60초 안에 | 약 **220건/초** |
| 푸시 직후 첫 10초 | 13,000 × 0.5 × 0.4 ÷ 10초 × 3요청 | 약 **780 RPS** |
| 스트레스 (50만 명) | 위 × 5 | 약 **3,900 RPS**, LLM 약 2,150 RPM |

- 읽기 급증은 평균이 아니라 **첫 몇 초**가 문제다. 평소 트래픽이 거의 0이다가 19:00:00에 수백~수천 RPS가 된다.
- LLM은 초당 건수보다 **공급사의 분당 요청·토큰 한도(RPM·TPM)**가 먼저 막힌다. 호출당 입력 2,000·출력 500토큰이면 430 RPM은 약 110만 TPM이다. 쓰려는 모델의 실제 한도를 확인해 이 표에 적는다.

### 3.2 기록 쓰기 계산

| 항목 | 계산 | 결과 |
| --- | --- | --- |
| 하루 세션 | 100,000 × 0.43 × 0.60 | 약 26,000개 |
| 하루 세트 행 | 26,000 × 25 | 약 **65만 행** |
| 1년 세트 행 | 65만 × 365 | 약 **2.4억 행** |
| 운동 후 동기화 피크 (19:00 운동자가 1시간 안에 전송) | 13,000 × 0.6 ÷ 3,600초 | 약 2건/초 (건당 최대 100세트 묶음) |
| `llm_call_log` | 하루 루틴 약 43,000 + 재시도 | 1년 약 1,600만 행 |

- 쓰기 요청 수는 작다. 문제는 **`workout_set`이 1년에 2억 행을 넘는다**는 것과, 과부하 규칙·LLM 맥락이 매일 "이 종목의 최근 2주 기록"을 읽는다는 것이다.

## 4. 설계

### 4.1 루틴 생성 배치

현재 설계(`docs/architecture.md`): 1분 스케줄러가 알림 30분 전 사용자를 골라 생성 → 후보 종목 SQL 필터 → LLM → 검증 → 실패 시 기본 루틴 → 캐시.

| 문제 | 설계 | 단계 |
| --- | --- | --- |
| 서버 여러 대가 같은 대상을 중복 생성 | 스케줄러는 ShedLock으로 한 대만 대상 선정. 저장은 `daily_routine (user_id, routine_date)` 유니크가 최후 안전망 | 1차 |
| 13,000건을 스케줄러 한 대가 직접 호출 | 대상 선정과 생성을 분리: 선정은 큐에 넣기만 하고, 워커 여러 대가 꺼내 생성 (Redis Streams + 소비자 그룹) | 3차 (FR-17) |
| LLM 한도 초과 | 전역 레이트 리미터(Redisson `RRateLimiter`)로 RPM·TPM을 공급사 한도 아래로. 서버 대수와 상관없이 하나의 한도를 공유 | 3차 |
| LLM 호출 수 자체가 많음 | **묶음 생성:** 분할 부위·장비·경력이 같은 사용자는 종목 구성을 한 번만 받고, 무게·세트·반복 수는 서버 규칙이 사용자별로 계산 (원칙상 숫자는 원래 서버가 계산) | 확장 (그룹 생성) |
| 알림 시각까지 생성이 안 끝남 | 마감 시각(예: 알림 2분 전)에 아직 `PENDING`이면 기본 루틴(`FALLBACK`)으로 확정하고 푸시. 늦게 온 LLM 응답은 버린다 | 1차 |
| LLM 장애 | 재시도 → (3차) 서킷 브레이커·보조 모델 → 기본 루틴 | 1차 / 3차 |
| 시간대 | `alarm_time`은 사용자 시간대 기준이라 "30분 안에 다가온 사용자"는 시간대별로 UTC 범위를 계산해서 고른다 | 1차 (명세에서 확정) |

측정: 시각별 대상 수, 생성 완료 시간(첫 건 ~ 마지막 건), 마감 시각까지 못 끝나 대체된 비율, LLM 호출 수·토큰·비용.

### 4.2 푸시 발송

| 문제 | 설계 | 단계 |
| --- | --- | --- |
| 같은 루틴에 알림 두 번 | `push_log (user_id, type, ref_id)` 유니크 | 1차 |
| 13,000건을 60초 안에 | 발송 대상을 미리 `push_log(PENDING)`으로 만들어 두고, 정각에 워커 여러 대가 나눠서 병렬 발송 (FCM HTTP v1, 동시 요청 수 제한) | 1차 단순 버전 → 3차 큐 |
| 만료된 토큰 | FCM 응답이 토큰 무효면 `TOKEN_EXPIRED` 기록 후 `device_token` 삭제 | 1차 |
| 푸시 직후 읽기 급증 | (선택) 발송을 0~30초 사이에 흩뿌려 첫 10초 피크를 낮춘다. "정각에 온다"는 제품 경험과 바꾸는 선택이라 측정 후 결정 | 검토 |

측정: 발송 완료 시간(첫 건 ~ 마지막 건), 실패율, 발송 후 열람까지 걸린 시간 분포(`opened_at - sent_at`).

### 4.3 푸시 직후 조회

목표(PRD 9장): 푸시 직후 오늘의 운동 조회는 캐시 응답, 일반 API p95 300ms 이하.

| 문제 | 설계 | 단계 |
| --- | --- | --- |
| 첫 조회가 DB로 감 | **생성 시점에 캐시를 채운다** (`routine:{userId}:{date}`, TTL 36시간). 푸시는 캐시가 채워진 뒤에만 나가므로, 정상 경로의 적중률 목표는 99% 이상 | 1차 |
| 캐시가 비었을 때 같은 키 요청이 동시에 DB로 | 키별 짧은 락(Redis `SET NX`)으로 한 요청만 DB를 읽고 나머지는 잠깐 기다렸다 캐시를 읽음 | 1차 (측정 후) |
| 인증 확인마다 DB 조회 | access 토큰은 서명 검증만 하고 DB를 읽지 않는다 (현재 구조 유지). refresh 갱신만 Redis 사용 | 구현됨 |
| 이벤트 기록 요청이 읽기와 같은 DB 커넥션을 씀 | `event_log` 저장은 비동기로 모아서 쓴다 (요청은 바로 응답) | 1차 (측정 후) |
| 커넥션 풀 고갈 | HikariCP 풀 크기·대기 시간을 부하 테스트로 정한다. 캐시 적중이면 DB 커넥션을 쓰지 않아야 한다 | 부하 테스트 |
| 서버 한 대로 부족 | 서버를 늘린다. 메모리에 상태가 없어서 로드 밸런서 뒤에 그대로 추가 가능 (원칙) | 3차 |

측정: 푸시 직후 60초 동안의 RPS·p95·p99, 캐시 적중률, DB 커넥션 사용량, 오류율.

### 4.4 기록 쓰기와 동기화

| 문제 | 설계 | 단계 |
| --- | --- | --- |
| 재전송·동시 전송으로 중복 | `(user_id, client_id)` 유니크 + upsert, `client_updated_at`이 더 최신일 때만 덮어씀 (last-write-wins) | 1차 |
| 100건 묶음을 한 건씩 저장 | 묶음 단위 한 번의 upsert (`INSERT ... ON DUPLICATE KEY UPDATE`) | 1차 (전후 처리량 비교가 PRD 기술 지표) |
| 최근 2주 기록 조회가 느려짐 | `(user_id, exercise_id, performed_at)` 인덱스로 사용자 범위만 읽음. 2억 행에서도 사용자별 범위는 작아서, 실행 계획과 시간을 시드 데이터로 확인 | 1차 |
| PR·주간 볼륨 계산 | 세션 종료 이벤트로 미리 집계 (`personal_record`, `weekly_volume`). 조회 시 원본 세트를 집계하지 않는다 | 1차 |
| 테이블 크기 | 아래 5장 | 검토 |

측정: 묶음 저장 전후 처리량, 재전송·동시 전송 시 중복 0건·유실 0건, 2억 행 시드에서 최근 2주 조회 p95.

### 4.5 챌린지 선착순 (동시성 실험)

- Redis Lua로 정원·중복 확인, DB 유니크 제약을 최후 안전망으로 (FR-51).
- 실험 목적은 기법 비교다: DB 비관적 락 vs Redis 원자 연산 vs 유니크 제약만, 같은 조건에서 TPS·p95·정원 초과·중복 수.
- 접속 대기열(FR-56)과 임시 확보·대기 승급(FR-52~55)은 실제 수요가 확인될 때 만든다.

## 5. 데이터 크기

| 테이블 | 1년 예상 (10만 명) | 방향 |
| --- | --- | --- |
| `workout_set` | 약 2.4억 행 | 지우지 않는 핵심 데이터. 우선 인덱스로 버티고 시드 데이터로 측정. **MySQL 파티셔닝은 파티션 키가 모든 유니크 키에 들어가야 해서** 현재 `(user_id, client_id)` 유니크와 시각 기준 파티션이 맞지 않는다. 필요해지면 ADR로 결정 |
| `llm_call_log` | 약 1,600만 행 | 보관 기간을 정하고(열린 질문), 기간이 지난 행은 정리. 시각 기준 파티션으로 오래된 파티션을 통째로 지우는 방식 검토 |
| `event_log` | 하루 수십만 행 | `llm_call_log`와 같음 |
| `push_log` | 하루 약 4.3만 행 | 지표 계산 기간이 지나면 정리 |

## 6. 인프라 확장 순서

필요가 측정으로 확인될 때만 다음 단계로 간다.

1. **서버 1대 + MySQL 1대 + Redis 1대** (최소 배포, PRD 11장 3단계)
2. 서버 여러 대 + 로드 밸런서 (상태 없는 서버라 코드 변경 없음)
3. 생성·발송 워커를 API 서버와 분리 (PRD 10장 "분리 대상": LLM 일괄 생성 워커)
4. MySQL 읽기 복제본 (캐시로도 DB 읽기가 병목일 때만. 복제 지연 때문에 "방금 저장한 기록 조회"는 원본에서 읽어야 함)
5. 카프카 (세션 종료 이벤트처럼 여러 소비자가 붙는 흐름이 생길 때만)

- Redis는 캐시·리프레시 토큰·레이트 리미터·큐를 모두 맡는 단일 장애 지점이다. Redis가 죽었을 때 각 기능이 어떻게 동작해야 하는지(캐시 → DB로 우회, 리프레시 → 재로그인 등)를 1차 배포 전에 정한다.

## 7. 부하 테스트 계획

- 환경: 운영과 같은 사양의 스테이징 VM (서버·MySQL·Redis 분리). 로컬 결과는 참고용으로만 쓴다.
- 데이터: 가입자 10만 명, 1년 치 세트(약 2.4억 행)를 시드 스크립트로 만든다. 빈 DB에서의 측정은 의미가 없다.
- 외부 API: LLM·FCM은 응답 지연을 흉내 내는 가짜 서버로 바꾼다 (비용과 공급사 한도 때문). 실제 LLM 한도는 문서 값으로 계산한다.
- 시나리오는 `load-test/<기능>.js`(k6), 결과는 `docs/load-tests/`에 `docs/templates/load-test.md` 양식으로 남긴다.

| 시나리오 | 부하 | 통과 기준 |
| --- | --- | --- |
| 푸시 직후 조회 | 0 → 780 RPS를 1초 안에, 60초 유지 (스트레스 3,900 RPS) | p95 300ms 이하, 오류율 0.1% 이하, 캐시 적중률 99% 이상 |
| 루틴 생성 배치 | 13,000명을 30분 안에 (가짜 LLM 응답 8초, 한도 430 RPM) | 마감 시각까지 100% 확정, 대체 비율 기록, 중복 생성 0건 |
| 푸시 발송 | 13,000건 | 60초 안에 발송 완료, 중복 발송 0건 |
| 기록 동기화 | 같은 묶음을 동시에 여러 번 재전송 + 정상 전송 혼합 | 중복 0건, 유실 0건, 묶음 저장 전후 처리량 비교 |
| 챌린지 신청 | 정원 100에 동시 10,000명 | 정원 초과 0건, 중복 0건, 방식별 TPS·p95 비교 |

부하 뒤에는 DB에서 정합성(중복, 정원 초과)을 읽기 쿼리로 직접 센다.

## 8. 관측

부하 테스트와 운영에서 같은 지표를 본다 (Prometheus + Grafana).

- API: 경로별 RPS, p50·p95·p99, 오류율
- 캐시: `routine` 캐시 적중률
- DB: HikariCP 활성·대기 커넥션 수, 느린 쿼리
- 생성 배치: 시각별 대상 수, 큐 길이, 완료 시간, 대체 비율
- LLM: 호출 수, 토큰, 실패율, 레이트 리미터 대기 시간
- 푸시: 발송 완료 시간, 실패율, 열람까지 걸린 시간

## 10. 이력서 표현 기준

실사용자 트래픽이 없으므로 "대규모 트래픽을 처리했다"고 쓰지 않는다. 가정과 재현을 밝힌다.

> 가입자 10만 명·알림 시각 쏠림 30%를 가정해 루틴 생성 배치와 푸시 직후 조회를 설계하고, k6로 순간 ○ RPS를 재현해 p95 ○ms → ○ms, 캐시 적중률 ○% 달성
