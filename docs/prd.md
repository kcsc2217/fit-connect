## 1. 한 줄 요약

내 신체 정보와 운동 기록을 아는 AI 트레이너가, 내가 정한 시각에 오늘의 운동과 식단을 짜서 알려주는 모바일 앱.

## 2. 배경과 문제

### 사용자 문제

- 헬스장에 가서 "오늘 뭐 하지?"를 매번 고민한다. 루틴 앱은 정해진 프로그램만 주고, 내 지난 기록에 맞춰 무게를 조절해주지 않는다.
- 범용 챗봇에 물어보면 매번 내 상황을 다시 설명해야 하고, 무게·칼로리 숫자가 그럴듯하게 틀린다.
- 헬스장 지하는 네트워크가 자주 끊겨서 기록 앱에 입력한 세트가 사라지거나 중복된다.
- 혼자 운동하면 꾸준함을 유지하기 어렵다.

### 프로젝트 배경 (개인 목표)

- 현재 회사(솔루션, 트래픽 없음)에서 얻기 어려운 **실사용자 운영, 트래픽·동시성 처리, LLM 서비스 운영** 경험을 직접 만든다.
- 결과물을 이력서 v6와 면접 소재로 쓴다. 대상은 1~3년차 백엔드 공고, B2C 서비스 회사.

## 3. 목표와 비목표

### 목표

1. 매일 설정한 시각에 "오늘의 운동"을 받아 바로 운동을 시작할 수 있게 한다.
2. 기록이 다음 루틴에 반영되어, 쓸수록 나에게 맞는 루틴이 나오게 한다.
3. 네트워크가 끊겨도 기록이 유실·중복되지 않게 한다.
4. (프로젝트 목표) 동시성, 대량 비동기 처리, LLM 운영을 측정 가능한 성과로 남긴다.

### 비목표

- 의료·재활 조언. 통증·부상 질문에는 전문가 상담을 권한다.
- 대규모 사용자 확보와 수익화. 실사용자는 본인과 지인 규모로 시작한다.
- 정밀한 영양 분석. 식단 기록은 LLM의 대략 추정치로 시작한다.
- 1차 단계의 MSA, 쿠버네티스, 카프카 도입.

## 4. 타깃 사용자

| 페르소나 | 특징 | 핵심 니즈 |
| --- | --- | --- |
| 꾸준히 하는 직장인 (주 사용자) | 운동 경력 1~3년, 주 3회, 퇴근 후 운동 | 고민 없이 오늘 할 운동 받기, 무게 진행 관리 |
| 다시 시작하는 사람 | 경력 6개월 미만 또는 공백 후 복귀 | 무리하지 않는 루틴, 질문할 곳 |
| 동기부여가 필요한 사람 | 혼자 하면 쉽게 그만둠 | 챌린지, 배지, 기록 성장 확인 |

## 5. 성공 지표

### 제품 지표 (1차 오픈 이후 측정)

| 지표 | 정의 | 초기 목표 |
| --- | --- | --- |
| 알림 열람률 | 운동 알림을 받은 사용자 중 앱을 연 비율 | 50% 이상 |
| 루틴 완료율 | 오늘의 운동을 열고 끝까지 기록한 비율 | 60% 이상 |
| 7일 재방문율 | 가입 후 7일 안에 운동일 기준 2회 이상 사용 | 50% 이상 |
| 루틴 만족도 | 운동 후 피드백 중 "적당했어요" 비율 | 60% 이상 |

### 기술 지표 (이력서 성과)

| 영역 | 지표 |
| --- | --- |
| 동시성 | 동시 신청 부하에서 정원 초과·중복 신청 0건, 방식별 TPS·p95 비교 |
| 동기화 | 재전송·동시 전송에서 중복 저장 0건, 유실 0건, 묶음 저장 전후 처리량 |
| LLM 운영 | 생성 실패율, 기본 루틴 대체율, 사용자당 토큰·일일 비용, 그룹 생성 전환 전후 호출 수 |
| 알림 | 사용자 N명 기준 생성 완료 시간, 푸시 직후 조회 p95와 캐시 적중률 |
| LLM 품질 | 평가 세트 규칙 위반율(프롬프트 버전별 전후), 존재하지 않는 종목 0건, 식단 목표 칼로리 오차 |
| LLM 안정성 | 단계적 대체(재시도 → 보조 모델 → 기본 루틴) 적용 후 생성 성공률 |
| LLM 비용 | 식단 추정 캐시 적중률, 프롬프트 캐싱 전후 비용 |
| 에이전트 | 통증 질문 시 도구 호출로 대체 루틴 제안·승인 적용 성공률 |
| 개발 체계 | API 1개 평균 개발 시간, AI 수정 반복 횟수, 훅이 잡은 오류 수 (ai-log 기준) |

### 이력서 문장 예시 (목표)

- 가상 프로필 40개 평가 세트로 프롬프트 개선 효과를 측정, 규칙 위반율 ○% → ○%
- 장비 조건 기반 후보 종목 필터로 존재하지 않는 종목 생성 0건
- 도구 호출 기반 AI 트레이너로 통증 질문 시 대체 루틴 제안·적용
- LLM 장애 시 보조 모델·기본 루틴 단계적 대체로 생성 성공률 99.○%

## 6. 범위와 출시 단계

주당 5~10시간 기준.

| 단계 | 범위 | 예상 | 기간 |
| --- | --- | --- | --- |
| 1차 오픈 | 로그인, 온보딩, 운동 기록, 오프라인 동기화, 오늘의 운동, 알림, LLM 평가·호출 로그 | 약 240시간 | 6~8개월 |
| 병행 | 챌린지 신청 API + 동시성 비교 실험 (앱 화면 없이) | 약 25시간 | 1차 중 |
| 2차 | 식단 추천·기록·캐싱, AI 트레이너 질문·도구 사용(축소판), 주간 리포트, (조건부) RAG | 약 90시간 | 약 3개월 |
| 3차 | 챌린지 앱·인증·배지, 임시 확보·대기열, 알림 생성 큐 전환, 부하 테스트, 서킷 브레이커·보조 모델, 프롬프트 캐싱 | 115~135시간 | 3~5개월 |
| 확장 | 그룹 생성, 포인트, 영상 분석 인증, 실시간 랭킹, 카프카 | 100시간 이상 | 이후 |

**이력서 v6 목표 시점:** 1차 오픈 + 챌린지 동시성 실험 완료.

## 10. 기술 방향 요약

- **앱:** Flutter, Riverpod, Drift(로컬 저장), FCM
- **서버:** Kotlin, Spring Boot 3, Spring MVC, JPA, MySQL 8, Redis, Flyway
- **아키텍처:** 모듈러 모놀리스 (user, workout, routine, notification, challenge, llm). 모듈 간 ID 참조, 내부 이벤트 연결
- **분리 대상:** LLM 일괄 생성 워커(3차), 영상 분석 워커(Python, 확장)
- **LLM 운영:** 후보 종목 SQL 필터, 평가 세트 + CI 채점, llm_call_log와 프롬프트 버전, Resilience4j(1차 재시도, 3차 서킷 브레이커·보조 모델). 벡터 검색은 지식 문서가 쌓일 때만
- **큐·카프카:** 내부 이벤트 → Redis Streams(3차) → 카프카는 여러 소비자가 붙는 흐름(신청 확정 이후 처리, 세션 종료 이벤트)에만, 측정 후 도입
- **운영:** Docker, GitHub Actions, 클라우드 VM, Prometheus·Grafana, k6
- **개발 체계:** Claude Code + CLAUDE.md, 훅, 스킬, ai-log 측정

상세는 trainer-ssaem-spec.md의 "기술 스택과 아키텍처" 참고.

## 12. 리스크와 대응

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 범위가 계속 커짐 | 완성 못 하고 중단 | 1차 범위 고정, 새 아이디어는 확장 목록에만 기록 |
| 앱 개발에 시간 과다 소요 | 백엔드 학습 시간 부족 | 최소 화면, AI 코딩 도구 적극 활용 |
| 새 언어 두 개 (Kotlin, Dart) | 초반 속도 저하 | 코루틴 등 고급 기능은 필요 시점까지 보류 |
| 실사용자가 적음 | 트래픽 성과 부족 | 부하 테스트로 재현, 한계를 정확히 표현 |
| LLM 비용 증가 | 운영 부담 | 호출 제한, 캐시, 그룹 생성 전환, 월 한도 |
| LLM 출력 오류 | 잘못된 루틴·식단 | 숫자는 서버 계산, 스키마 검증, 안전 규칙, 대체 응답 |
| 구직이 뒤로 밀림 | 이직 지연 | 1~3년차 공고 지원을 프로젝트와 병행 |
| LLM 기능 비중이 커짐 | 백엔드 포지셔닝이 흐려짐 | 동시성·동기화·트래픽 실험을 중심에 두고, LLM 운영은 차별화 요소로 유지 |
| 평가 세트 구축 부담 | 1차 일정 지연 | 20개로 시작해 점진적으로 40개까지 확장 |
| 필요 없는 기술 도입 | 면접에서 도입 이유 설명 불가 | 벡터 검색·카프카 등은 측정으로 필요가 확인될 때만 도입 |
