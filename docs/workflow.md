# 작업 절차

AI를 그때그때 쓰지 않고, 매번 같은 품질로 일하게 하기 위한 절차. 기능 하나를 이 순서로 만든다.
원본 가이드는 `ai-dev-workflow.md`(개발 체계 가이드).

## 작업 크기 (S/M/L)

작업을 시작할 때 Claude가 크기를 제안하고 사용자가 확정한다. 크기는 걸리는 시간이 아니라 **위험도**로 정한다.

| 크기 | 기준 | 예시 |
| --- | --- | --- |
| **S** | 기존 코드 수정, 필드·검증 추가, 버그 수정. 새 테이블·새 API 없음 | RPE 범위 검증 추가, 응답 필드 이름 변경 |
| **M** | 새 API 1~2개, 또는 테이블 추가 | 내 정보 조회 API, 온보딩 프로필 저장 |
| **L** | 동시성·멱등성·LLM·외부 연동이 걸리거나 설계 판단이 필요한 기능. 여러 API·모듈에 걸침 | 오프라인 동기화, 오늘의 운동 생성, 챌린지 선착순 신청 |

- **동시성·멱등성·LLM이 걸리면 작아 보여도 최소 M**으로 본다.
- 작업 중 예상보다 커지면 멈추고 크기를 다시 정한다 (S → M이면 계획 모드부터).

## 크기별 단계

| 단계 | 하는 일 | 스킬 | 결과물 | S | M | L |
| --- | --- | --- | --- | --- | --- | --- |
| 1. 명세 | PRD·기능 명세에서 해당 기능만 뽑아 정리 | `/spec` | `docs/specs/<기능>.md` | - | ○ | ○ |
| 2. 계획 | 계획 모드로 계획 작성 → **계획 패널에서 승인** → 파일로 저장 | `/plan-feature` | `docs/plans/<번호>-<기능>.md` | 채팅 승인 | ○ | ○ (M 단위로 쪼갬) |
| 3. 테스트 먼저 | 계획의 테스트 목록부터 작성 (실패하는 상태) | (`/plan-feature`에 포함) | 테스트 코드 | ○ | ○ | ○ |
| 4. 구현 | 테스트가 통과할 때까지 구현 | `/new-api` | 컨트롤러·서비스·DTO | ○ | ○ | ○ |
| 5. 리뷰 | 리뷰 에이전트가 체크리스트로 변경분 검토 | `/review-change` | 리뷰 결과 | - | ○ | ○ |
| 6. 성능 확인 | 쿼리 수·실행 계획, 필요하면 부하 테스트 | 직접 요청 | `docs/perf/`, `docs/load-tests/` | - | 조회 API면 | ○ |
| 7. 기록 | 설계 판단은 ADR, 작업 결과는 ai-log | 직접 요청 | `docs/decisions/`, `docs/ai-log.md` | - | ai-log | ADR + ai-log |

모든 크기에서 훅이 수정마다 포맷·컴파일을, 작업 종료 시 테스트를 자동으로 확인한다.

## 스킬이 없는 단계 (6·7단계)

스킬은 반복이 확인된 단계만 만든다. 6·7단계는 아래처럼 직접 요청하고, 같은 요청을 세 번 반복하면 스킬로 만든다.

| 단계 | 요청 예시 | 지킬 것 |
| --- | --- | --- |
| 쿼리 확인 | "동기화 API 통합 테스트를 Hibernate 통계 켜고 돌려서 쿼리 수 확인해줘. 데이터 1건, 10건 비교" | 건수에 따라 쿼리 수가 늘면 N+1. EXPLAIN은 **읽기 전용 계정, 개발 DB만** |
| 부하 테스트 | "챌린지 신청 k6 시나리오 만들어줘. 결과는 `docs/templates/load-test.md` 양식으로" | 실행 전 시나리오 승인. 운영 서버 금지. 부하 후 DB에서 정합성 직접 확인 |
| ADR | "동기화 충돌 정책 ADR 써줘. `docs/templates/adr.md` 양식으로" | 결정·이유를 지어내지 않고 모르면 묻는다 |
| ai-log | "이번 작업 ai-log에 기록해줘" | `docs/ai-log.md`의 기록 규칙을 따른다 |

- **S 채팅 승인:** 고칠 파일, 바꿀 내용, 추가할 테스트를 3~5줄로 말하고 "진행할까요?"로 승인받는다. 계획 파일은 만들지 않는다.
- **L 쪼개기:** 계획 하나가 M 크기가 되도록 나눈다 (예: 001 엔티티·제약, 002 동기화 API). 각 계획마다 2~7단계를 반복한다.

## 코드를 확인하는 곳

| 시점 | 어디서 | 보는 것 |
| --- | --- | --- |
| 구현 전 | 앱의 계획 패널 (계획 모드) | 계획 전체와 **핵심 코드 스케치**. 승인 버튼을 눌러야 코드 수정이 시작된다 |
| 구현 전 | `docs/plans/<번호>-<기능>.md` | 승인된 계획의 기록 |
| 구현 후, 커밋 전 | 앱의 diff 패널 | 실제로 바뀐 코드 전체. 스케치와 다르게 구현된 곳이 있는지 확인 |

**핵심 코드 스케치**(M/L 계획에 포함)에는 판단이 들어가는 부분만 넣는다: 핵심 메서드 시그니처와 분기, 동시성·멱등성 처리, 유니크 제약·인덱스, 복잡한 쿼리. 컨트롤러·DTO처럼 정해진 구조대로 만드는 코드는 넣지 않는다.

## 규칙

- **2단계에서 반드시 멈춘다.** 계획이 승인되기 전에는 코드를 쓰지 않는다. M/L은 계획 모드라서 승인 전에는 파일 수정 자체가 막힌다.
- 승인 후 계획이 바뀌면 `docs/plans/`의 문서를 먼저 고치고 다시 승인받는다.
- 승인할 때는 기능 설명보다 **테스트 목록**을 꼼꼼히 본다. AI가 테스트와 구현을 둘 다 쓰므로, 테스트 목록이 품질을 정한다.
- 4단계에서 테스트를 통과시키려고 테스트를 고치지 않는다. 테스트가 틀렸다면 이유를 말하고 승인받는다.
- 같은 요청을 세 번 반복하면 그 단계를 스킬로 만들거나 기존 스킬을 고친다.
- AI가 같은 실수를 두 번 하면 CLAUDE.md에 규칙을 한 줄 추가한다.
- 단계별 스킬이 안정되면 `feature` 스킬 하나로 전체를 묶는다. 단, 계획 승인 단계는 그대로 둔다.

## 리뷰 체크리스트

`.claude/agents/reviewer.md`가 이 목록으로 검토한다.

- [ ] 엔티티를 직접 반환하지 않는가
- [ ] N+1 쿼리가 없는가
- [ ] 동시 요청 시 정합성이 깨질 곳이 없는가
- [ ] 재전송돼도 안전한가 (멱등성)
- [ ] LLM 응답을 검증 없이 쓰지 않는가
- [ ] 실패·타임아웃 시 대체 경로가 있는가
- [ ] 테스트가 정상·실패·경계 케이스를 다루는가
- [ ] 도메인 간 참조 규칙과 Given-When-Then 테스트 규칙을 지키는가
